# Field Test Case：用戶看不懂 markdown 符號（`**` / `>`）

- 日期：2026-07-26
- 回報者：Pearl（ART，team09）、Jessie Chen（內測 tester）
- 類型：**UX 認知落差** — 非技術用戶對開發者習以為常的符號的真實反應
- 嚴重度：🔴 高（影響每一則 AI 訊息的可讀性、且用戶會停下來猜測而中斷心流）
- 狀態：✅ 已修（v1.5.x、2026-07-26）

## 2. 用戶實際看到的畫面

```
**今天 Day 12「W2 整合輕」**

**目標**：跑完 4 步，不升級成吵架。

• **觀**：聽她的立場 + 你自己的事實
• **感**：你自己當下的感受

> **你內在需要的是什麼**
- 你需要**被她信任**嗎？
```

`**`、`>`、`---` 全部裸露。

---

## 3. Root cause

兩個原本各自合理的決定，疊在一起造成問題：

| 層 | 狀況 |
|---|---|
| **Prompt 層** | `buildContext.ts` 本身是用 markdown 撰寫的（含 **425 處 `**`**），LLM 自然模仿此風格輸出 |
| **UI 層** | 聊天泡泡是 `<p className="whitespace-pre-wrap">{content}</p>` **純文字**輸出、不渲染 markdown |

→ AI 寫 markdown、UI 不渲染 → 語法整個曝露給用戶。

同樣問題也存在於：課程知識卡片（`course_content.knowledge_point` 也含 markdown）、PDF export。

---

## 4. 解法決策：選「渲染」而非「改 prompt」

當時有兩條路：

| | 🅰️ UI 渲染 markdown | 🅱️ 改 prompt 少用 `**`、改用「」 |
|---|---|---|
| 動到 `buildContext.ts` | ❌ 不用 | ✅ 要（Steve 核心 IP、CLAUDE.md 禁區） |
| 既有對話 | ✅ **回溯修好**（Pearl / Angel 的 21 天紀錄立刻變好看） | ❌ 只影響未來訊息 |
| 風險 | 零（不改 AI 行為） | 425 處要逐一評估、LLM 天生愛用 markdown 難戒斷 |
| 工時 | ~30 分鐘 | 數小時 + 需回歸測試 |

**Steve 拍板 🅰️**。

理由不只是成本 —— Pearl / Angel 的 21 天對話要當 **case study 行銷素材**，回溯生效這點是關鍵。

### 上線後的觀察（重要）

原本擔心「渲染後粗體太多會很吵」，實測後**沒有**。
AI 用粗體其實很克制，都落在該強調的位置（小標、關鍵詞、重點句），
渲染後反而讓段落有了呼吸感與層次。

→ **🅱️ 判定不需要做**。`buildContext.ts` 完全沒被碰到。

## 5. 實作

新增 `src/components/MarkdownMessage.tsx`（chat + PDF export 共用）：

- 用已安裝的 `react-markdown` + `remark-gfm`（admin spec viewer 也在用、不新增依賴）
- `blockquote`：Pearl 橘色左邊線 `#EF9F27` + 淡橘底
- `strong` / 條列 / 標題 / 分隔線 / 表格 / code 全套 Pearl 風格
- `print` prop：PDF 模式拿掉背景色只留左邊線（瀏覽器列印預設會濾掉背景）
- `preserveSingleLineBreaks()`：段落內單換行轉 markdown 硬換行、保留原視覺節奏
- `stripMarkdown()`：給需要 `line-clamp` 的地方用（markdown 多 block 元素會讓 line-clamp 失效）

套用 3 處：chat AI 泡泡、課程知識卡片、PDF export AI 泡泡。

**User 自己打的字維持純文字** —— 用戶不會寫 markdown，渲染反而會吃掉他打的 `*` 或 `#`。

## 6. Takeaways

### 對產品

1. **「開發者覺得理所當然」≠「用戶看得懂」**
   `**` 在工程圈是常識，但 Pearl 的參考框架是「密碼遮蔽用 ***」、Jessie 是「亂碼」。
   兩個人都是聰明的成年人，卻都卡在同一個地方。

2. **卡住的成本不只是「看不懂」**
   Pearl 說「反覆看了很多次才理解」—— 這是**心流中斷**。
   小羽正在做 PROBE 深層探問時，用戶注意力卻被符號拉走，傷害的是對話品質本身。

3. **修 UI 比修 AI 便宜且安全**
   同一個症狀，往上游改（prompt）成本高風險高，往下游改（渲染層）成本低風險低。
   下次遇到類似問題，先問：「這能不能在呈現層解決？」

### 對流程

4. **內測群的閒聊是金礦**
   這則回饋沒有走任何正式管道，是 Pearl 在 LINE 隨口說的。
   要保持這種低摩擦的回饋通道，並且**真的去看**。

5. **修完要回頭驗證假設**
   「粗體會不會太吵」是實作前的擔憂，實測後證明多餘。
   若當時因為這個擔憂而選了 🅱️，就會白白動到核心 IP。
